# Plan 13d: `propose_data_architecture` Orchestrator

**Complexity: Medium.** Ties Stage 5 (per-step classification) + Stage 6 (entity
derivation) + validation into one real, persistable `DataArchitecture`, mirroring
`propose_component_tree`'s exact retry shape (11l). Proceeds through Build/Test/Commit per
the Autonomy Default.

## Requirement

Part of `13.data-architecture-layer.md`. R41 (derived from an already-frozen Workflow
Tree), R43/R44 (no duplicate entities, every anchor a real compound key).

## Scope decisions

1. **Runs Stage 5 across every real Atomic step in the given Workflow Tree**, collects the
   `(step, operation)` pairs for every non-`None` classification, then makes exactly one
   Stage 6 call with that whole set — matches 13b's own scope decision 2 (dedup needs the
   whole set at once).
2. **`validate_data_architecture(architecture, workflow_tree) -> ValidationResult`** is a
   real, independent safety net over Stage 6's own internal dedup — same reasoning
   `check_attribute_leaf` (11h) gave for the Component Tree side: an inner loop trying to
   prevent a problem is not the same as a whole-result check that actually catches it if it
   slips through. Checks: every entity has a non-empty name and at least one primary key;
   no two entities share a name; every anchor's `node_id` is a real Atomic step in
   `workflow_tree` and every anchor's `data_id` is a real entity in the same result.
3. **Same bounded retry shape as `propose_tree`/`propose_component_tree`**
   (`MAX_DATA_ARCHITECTURE_RETRIES = 3`), re-running the whole Stage 5/6 pass with the
   specific violations appended to context on failure — consistent posture, even though a
   validation failure here would more likely indicate a genuinely malformed AI response
   (an anchor referencing a nonexistent step/entity) than a content-quality issue, since the
   mechanism costs little to keep consistent and does add real robustness.

## Build (`backend/data_architecture/engine.py`)

`validate_data_architecture(architecture, workflow_tree) -> ValidationResult`;
`propose_data_architecture(domain, workflow_tree, reasoning_context) -> Tuple[
DataArchitecture, ValidationResult]`.

## Test (`tests/test_data_architecture.py`)

1. Happy path: mocked Stage 5 (per-step, keyed on step label) + Stage 6 (one call) produce
   a real `DataArchitecture` from a small Workflow Tree fixture; `validation.passed`.
2. A step Stage 5 classifies as `TRANSIENT` produces no anchor at all (confirms Stage 5's
   `None` result is honored end to end, not silently coerced into a fabricated operation).
3. `validate_data_architecture` catches a hand-built architecture with two entities sharing
   the same name, and one with an anchor pointing at a nonexistent Atomic step id.
