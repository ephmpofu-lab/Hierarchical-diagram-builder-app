# Plan 11b: Capability Identification Stage (Stage -2)

**Complexity: Simple.** Same shape as 11a: one new model, one new AI-calling function in
the existing `backend/component/engine.py`, no schema-breaking changes. Proceeds through
Build/Test/Commit per the Autonomy Default.

## Requirement

R25 (`ARCHITEQ-PRD.md`): "The system groups extracted requirements into discrete
capabilities; every capability carries a `traced_requirements[]` field and is rejected if
empty (Stage -2, Capability Identification; CD1)."

## What this sub-plan does NOT do

Does not build Stage -1/0, does not add an API endpoint (same reasoning as 11a — the
endpoint arrives with 11d's orchestrating function). Does not persist anything.

## Build

1. **`backend/models.py`** — new model:
   ```python
   class Capability(BaseModel):
       label: str
       traced_requirements: List[str] = Field(default_factory=list)
       domain: str
   ```
2. **`backend/component/engine.py`** — new function:
   ```python
   def identify_capabilities(
       domain: str, requirements: List[ExtractedRequirement], reasoning_context: str
   ) -> List[Capability]:
   ```
   One AI call, same `_ask_json` convention. Prompt: given the domain and Stage -3's
   extracted requirements (each shown with its real `prd_requirement_id`), group them into
   discrete capabilities, each listing which of the given requirement ids it groups — never
   inventing a requirement id not in the input list. A returned capability whose
   `traced_requirement_ids` end up empty after filtering against the real input ids (either
   the model returned none, or it returned only invented ids that got filtered out) is
   rejected outright, not returned with an empty list — this is CD1's own predicate, not a
   separate Validator pass layered on top.

## Test (`tests/test_engineering_decomposition.py`)

1. Mocked `_ask_json` returns 2 well-formed capabilities, each with valid
   `traced_requirement_ids` — confirm `identify_capabilities` returns exactly 2
   `Capability` objects with the right `traced_requirements` and `domain`.
2. Mocked `_ask_json` returns one capability with an empty `traced_requirement_ids` list
   and one with only an invented id not present in the input requirements — confirm both
   are rejected (dropped), only genuinely-traced capabilities are returned.
3. Confirm the prompt passed to `_ask_json` includes each input requirement's real
   `prd_requirement_id` (regression guard against a prompt that silently drops them).
