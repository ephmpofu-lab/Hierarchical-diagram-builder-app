# Plan 11d: Component Attribute Enumeration (Stage 0)

**Complexity: Medium.** Larger than 11a-11c: introduces a recursive bounded split loop
(mirroring `backend/decompose/engine.py`'s `_split_step` pattern) and a cross-component
Validator-style check, not just a single filtered AI call. Proceeds through Build/Test/
Commit per the Autonomy Default (Medium doesn't require a DP9 pause).

## Requirements

- R27: "The system enumerates each component's configuration attributes down to
  single-name, single-type leaves; a leaf requiring 'and' to describe its meaning is
  rejected and must be split (Stage 0, Component Attribute Enumeration; CD4)."
- R28: "No two components in a Component Tree claim the same attribute or responsibility
  (CD5)."

## What this sub-plan does NOT do

Does not freeze the actual Component Tree (that's 11e's Reconciliation Rule + the future
orchestrator in a later sub-plan) — this sub-plan produces attributes per-component and a
cross-component check function; wiring them into one frozen tree object is out of scope
here. Does not persist anything.

## Build (`backend/models.py`, `backend/component/engine.py`)

1. **`Attribute` model**:
   ```python
   class Attribute(BaseModel):
       name: str
       type: str
       component_label: str
       domain: str
   ```
2. **`MAX_ATTRIBUTE_SPLIT_DEPTH = 3`** — same fixed-constant posture as
   `MAX_ATOMICITY_SPLIT_DEPTH` elsewhere in this codebase.
3. **`_attribute_needs_split(name)`** — CD4's own literal test: `True` if the name contains
   " and " or "&". This is deliberately simpler than the Workflow Tree's formal 5-criterion
   Atomicity Test (P1) — CD4 states its own single criterion directly, it doesn't inherit
   P1's full test.
4. **`_split_attribute(name, type_, reasoning_context)`** — one AI call asking the model to
   split one compound attribute into two or more atomic ones. Mirrors `_split_step`'s role
   for atomic steps, at the attribute level.
5. **`enumerate_attributes(component, reasoning_context) -> List[Attribute]`** — one AI call
   proposing candidate attributes for the component, then a bounded queue-based loop
   (depth-tracked, capped at `MAX_ATTRIBUTE_SPLIT_DEPTH`) that splits any candidate failing
   `_attribute_needs_split`, same shape as the existing atomic-step split loop. A candidate
   with an empty name or type after the loop settles is dropped (defensive filter, same
   posture as 11a-11c).
6. **`check_no_shared_attributes(attributes) -> List[str]`** — R28/CD5's cross-component
   check, operating over the full set of attributes across every component in a domain
   (not per-component, unlike `enumerate_attributes`). Returns one human-readable violation
   message per attribute name claimed by more than one component; empty list if none. Kept
   in `backend/component/engine.py` for now rather than a new `backend/validator/component_*`
   module — one function doesn't warrant a new file yet, same reasoning already applied
   elsewhere in this corpus ("don't add a file for one rule").

## Test (`tests/test_engineering_decomposition.py`)

1. `enumerate_attributes` with a mocked response of 3 clean candidates — confirm 3
   `Attribute` objects returned, each stamped with the right `component_label`/`domain`.
2. `enumerate_attributes` with one candidate whose name contains "and" — mock the follow-up
   split call to return 2 pieces — confirm the final result has the compound candidate
   replaced by its 2 split pieces, not the original compound one.
3. `enumerate_attributes` bounds recursion: a split response that itself still contains
   "and" is only retried up to `MAX_ATTRIBUTE_SPLIT_DEPTH`, then the last attempt is kept
   as-is rather than looping forever.
4. `check_no_shared_attributes` — a hand-built attribute list with one name claimed by two
   components returns exactly one violation message naming both; an attribute list with no
   overlaps returns an empty list.
