# Plan 13f: ERD Renderer

**Complexity: Medium.** New SVG renderer with its own layout algorithm, reusing 10a-iii's
`roundedPolylinePath` for connector geometry. Proceeds through Build/Test/Commit per the
Autonomy Default.

## Requirement

Part of `13.data-architecture-layer.md`. R45 (entity boxes from the canonical model), R46
(own layout, independent of the Workflow Tree/n8n canvas), spec sections 9-10/19-20.

## Scope decisions

1. **The Data Layer toggle attaches to n8n mode specifically, not Python mode.** Data
   Anchors describe what a workflow *node* does to persistent data (spec section 5); this
   app's concrete "node" UI is the n8n canvas's node tiles (10a-10b), not the Python
   folder/file/function browser. A "Workflow | Data" layer toggle is added inside n8n
   mode's output section, alongside (not replacing) the existing Python|n8n mode toggle.
2. **Own FK-driven layered layout, not the Tree Diagram's/n8n canvas's** (R46): entities
   with no FK dependency are level 0; an entity referencing a level-N entity sits at level
   N+1 (longest-path layering over the same FK graph `_topological_order_by_fk` already
   computes server-side, recomputed client-side over the fetched `DataArchitecture`
   response — no new backend endpoint needed, the data is already in hand). Entities within
   a level are arranged left to right; levels stack top to bottom, matching the spec's own
   worked vertical-chain example.
3. **Collapsed by default, expand on click** (spec section 19): collapsed shows Data ID +
   name + platform; expanded shows the full attribute list with PK/FK badges — mirrors
   10c's own collapsed/expanded convention, not a new visual idiom.
4. **Relationship lines reuse `roundedPolylinePath`** (10a-iii) for the connector geometry
   between entity boxes, with the real cardinality (`1:N`, etc.) labeled at the midpoint —
   never a raw straight/diagonal line (R20).

## Build (`static/js/decompose.js`, `static/css/style.css`)

1. `computeErdLayout(architecture)` — FK-graph layering (longest-path from entities with no
   outgoing FK), assigns `{x, y}` per entity box.
2. `renderErdDiagram(architecture)` — entity boxes (collapsed/expanded via click, toggled
   per-entity in a small local state map), relationship lines with cardinality labels.
3. A "Workflow | Data" toggle inside n8n mode's `renderOutputSection` branch; fetches
   `GET .../data-architecture` once per domain (cached in `state.dataArchitecture`, reset
   on domain change, mirroring `n8nRender`'s own cache convention) when Data is selected
   for the first time.
4. CSS: `.decompose-erd-entity`, `.decompose-erd-entity-collapsed/-expanded`,
   `.decompose-erd-attribute-row`, `.decompose-erd-pk-badge`/`-fk-badge`,
   `.decompose-erd-relationship`, `.decompose-erd-cardinality-label` — existing tokens
   only, no new colors.

## Test

Standalone Playwright harness (this session's own established pattern): a hand-built
3-entity, 2-relationship fixture (`documents -> document_chunks -> embeddings`, matching
the spec's own worked example) confirms: 3 collapsed entity boxes render with correct
IDs/names; clicking one expands it to show its real attributes with correct PK/FK badges;
2 relationship lines render with the correct cardinality labels; entities are laid out in
levels matching the FK chain (not the Tree Diagram's own layout constants). Zero JS errors.
