# Plan 13: Data Architecture Layer (Module 13)

**Complexity: Complex.** A second, synchronized architectural layer derived from an
already-frozen Workflow Tree, per `docs/ARCHITEQ-Data-Architecture-Layer-Spec.md` and
`ARCHITEQ-PRD.md` R41-R50. Mirrors Module 11's own precedent (a Complex, tree-derived layer
built as backend stages first, then a real orchestrator + API, then frontend) — broken into
sub-plans per DP5/DP9; this file is the index only.

## Grounding decisions (resolved before any sub-plan starts)

1. **Workflow ID = domain name; Node ID = real `TaskTreeNode.id` (Atomic step level
   only).** The spec's own "WF01/WF02" framing assumes multiple named workflows per system;
   ARCHITEQ has exactly one Workflow Tree per domain, already mapping 1:1 to one exportable
   n8n workflow. No new multi-workflow concept is invented — this reuses what's already
   real (see the spec doc's own added grounding note, OQ7).
2. **Data Architecture is derived, never authored independently** (R41) — mirrors Module
   11's Component Tree: the Workflow Tree freezes first (already true, Module 5), a new
   Stage 5 (persistence classification) and Stage 6 (entity derivation) run only against an
   already-frozen tree, producing a separate, persisted `DataArchitecture` object.
3. **One canonical model, three derived views** (R45): a `DataEntity` (name, attributes,
   PK/FK, constraints, relationships) is the single source; SQL DDL, the rendered ERD, and
   the workflow-to-data anchors are all pure functions of that same model — never
   independently authored.
4. **PostgreSQL only** for generated SQL DDL (matches this app's own real stack and the
   spec's own worked examples — `UUID`, `TIMESTAMPTZ`, `JSONB`).
5. **The ERD gets its own layout algorithm**, independent of the Tree Diagram's/n8n
   canvas's layout (R46) — arranged by FK relationships (a simple layered/chain layout,
   not a generic graph-layout library this app doesn't have), reusing 10a-iii's
   `roundedPolylinePath` routing helper for the connector geometry, not its stage-zone
   layout (that's Workflow-Tree-specific).
6. **Prominence toggling is a real, new canvas capability** (R47-R48/R9 in the spec doc):
   Workflow-active/Data-underlay and Data-active/Workflow-underlay, never equal weight —
   built as an extension of the existing n8n canvas (10a-10b), not a new page.

## Sub-plans

### Backend (data model + derivation pipeline)

1. **13a.data-entity-model-and-persistence.md** — `DataEntity`, `DataAttribute`,
   `DataRelationship`, `DataAnchor`, `DataArchitecture` container models;
   `backend/data_architecture/repository.py` (mirrors `component/repository.py`'s exact
   convention, `data_architectures/{domain}.json`). **Built, tested, committed.**
2. **13b.persistence-classification-and-entity-derivation.md** — Stage 5 (classify every
   Atomic step's operation: CREATE/READ/WRITE/UPDATE/DELETE/QUERY/TRANSIENT) + Stage 6
   (propose/dedupe persistent Data Entities for steps that need one, produce `DataAnchor`
   rows). One new package, `backend/data_architecture/engine.py`. **Built, tested,
   committed** — Stage 6 derives entities for a whole domain in one call (resolves OQ8 for
   derivation specifically), so deduplication actually works; N:M relationships
   deliberately not specially derived (emerge naturally via a join entity's two FKs).
3. **13c.sql-ddl-generator.md** — deterministic (no AI) `render_sql_ddl(entities,
   relationships) -> str`, PostgreSQL dialect, mirrors `python_renderer.py`'s pure-function
   style. **Built, tested, committed.**
4. **13d.propose-data-architecture-orchestrator.md** — ties Stage 5/6 + validation (no
   duplicate entities for the same real object, every `DataAnchor` references a real
   Atomic step and a real Data ID) into one `propose_data_architecture` call, mirroring
   `propose_component_tree`'s exact retry shape. **Built, tested, committed.**
5. **13e.data-architecture-api.md** — minimal endpoints mirroring the Component Tree's own
   shape: `POST .../data-architecture/draft`, `/approve`, `GET .../data-architecture`.
   **Built, tested, committed.** Backend for Module 13 (13a-13e) is now feature-complete;
   remaining sub-plans (13f-13j) are all frontend.

### Frontend (ERD renderer + dual-layer canvas)

6. **13f.erd-renderer.md** — the Data Layer's own view: entity boxes (collapsed/expanded
   per R19-equivalent), attribute rows with PK/FK badges, relationship lines with
   cardinality, own FK-driven layout (not the Tree Diagram's).
7. **13g.workflow-active-anchors-and-underlay.md** — compact Data Anchors on n8n node
   tiles when Workflow is the active layer; faint, real (never decorative) Data Layer
   reference underneath.
8. **13h.data-active-mode-and-underlay.md** — the reverse: ERD at full prominence, faint
   real Workflow reference underneath, named workflow/domain + real node ids.
9. **13i.bidirectional-highlighting.md** — select a node -> highlight its data
   entities/operations; select an entity -> highlight every referencing node (across
   domains, per the compound key); cross-layer lines revealed only on hover/select, hidden
   otherwise (not permanently drawn, per R48/section 14).
10. **13j.table-detail-panel-and-sql-view.md** — selecting an entity opens a detail panel
    (id, name, description, platform, attributes, PK/FK, constraints, relationships,
    workflow usage, node mappings) with a copyable SQL view, mirroring the existing Node
    Detail Panel's own drawer pattern.

## Explicitly deferred / out of scope

Multiple SQL dialects (Postgres only, per the Non-Goals addition). Executing generated SQL
against a real database. Cross-system data lineage / master data management beyond one
domain's own derived model. A full "Layer Controls" settings panel beyond the minimal
Active/Underlay toggle R47 requires (indexes/constraints display beyond what the detail
panel already shows is real content, not a separate configuration surface).
