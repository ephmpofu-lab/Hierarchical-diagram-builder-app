# Plan 13i: Bidirectional Highlighting (Workflow -> Data half)

**Complexity: Simple.** Extends the already-existing Node Detail Panel (10b-ii's drawer),
does not duplicate 13j's own table-detail-panel scope. Proceeds through Build/Test/Commit
per the Autonomy Default.

## Requirement

Part of `13.data-architecture-layer.md`. R49 (selecting a node highlights its data
entities/operations), spec section 13 (WORKFLOW -> DATA direction) and section 15 (select
highlights the related side).

## Honest scope narrowing, decided before building

Traced the spec's own sections 13-15 against what this app's canvas can actually show today:
the DATA -> WORKFLOW direction ("click a table, highlight every referencing node") is
already 13j's own listed scope (R50's "workflow usage" field on the table detail panel) --
building it again here would duplicate that work, not add to it. The spec's own hover-
reveal *connector lines* between a node and a faint underlay entity (section 14-15) assume
both layers render as positioned, coordinate-addressable boxes at once; 13g/13h's faint
underlay is deliberately a text-only reference panel (a real, stated choice made in 13g's
own plan, to avoid a rendered-behind-the-nodes ERD risking exactly the "must not interfere
with workflow readability" failure the spec itself warns against) -- there are no two
coordinate spaces to draw a connector line between yet. Rather than fake a line to nothing,
this sub-plan's real, honest scope is the WORKFLOW -> DATA half only: the already-existing
Node Detail Panel gains a real "Data" section showing that node's own actual `DataAnchor`
rows (entity id/name + operation) whenever a Data Architecture is loaded, regardless of
which layer is currently the active one. A literal cross-layer connector-line reveal is
named here as a real, deferred enhancement, not silently dropped.

## Build (`static/js/decompose.js`)

`renderNodeDetailPanel`: when `state.dataArchitecture` is loaded, look up
`state.dataArchitecture.anchors` filtered to the selected node's real id; if any exist,
render a "Data" section (mirrors the drawer's existing `metaRow`/section-label pattern)
listing each anchor's entity id + name + operation.

## Test

Standalone Playwright harness: selecting a node with 2 real anchors shows a "Data" section
listing both (entity id/name + operation); selecting a node with none shows no such
section; the section is absent entirely when `state.dataArchitecture` is still `null`
(not yet fetched).
