# Plan 11g: n8n Hover-Payload

**Complexity: Simple.** Frontend-only, no backend change needed — same "already-fetched
data, just join it client-side" pattern as 10c/12a. Proceeds through Build/Test/Commit per
the Autonomy Default.

## Requirement

R31 (`ARCHITEQ-PRD.md`): "The n8n Renderer's node graph supports hover-reveal: hovering any
node shows its `requires`/`produces`/`rules` data contract and any intermediate objects
passing through it, sourced directly from those fields, never a separately invented
description."

## Where this lives, and a note on sequencing

`static/js/decompose.js`'s *current*, already-shipped `renderN8nDiagram` (the simpler
AMENDMENT-4-era n8n SVG, not the not-yet-built 10a canvas-foundation rebuild). Building this
against the current renderer rather than waiting for 10a because R31 is independently real
and useful now, and the hover mechanism itself (data lookup + tooltip positioning) is
renderer-agnostic. **Flagged explicitly**: when 10a eventually replaces `renderN8nDiagram`'s
internals (stage-zone layout, rounded-orthogonal routing), this hover behavior must be
carried forward into the new node-tile rendering, not dropped — 10a's own plan file should
note this dependency when that sub-plan starts.

## What "intermediate objects passing through it" means here

Interpreted literally from the real fields already on every `TaskTreeNode`, never invented:
`consumes` (the single named input), `produces` (the output), `requires` (resolved to the
labels of the steps it depends on, not raw ids), `rules` (real constraints), and
`variables` (the actual config values flowing through/configuring this step — this is what
"intermediate objects passing through it" concretely maps to, since these are the only
per-step data fields that aren't already requires/produces/rules).

## Build (`static/js/decompose.js`, `static/css/style.css`)

1. **A tooltip element**, created once and reused (same pattern as the reference mockup's
   `#n8n-tooltip`, reskinned to this app's own tokens): fixed-position, hidden by default,
   populated and shown on hover.
2. **`showN8nHoverPayload(evt, node)`** — looks up `state.tree.nodes[node.step_id]`,
   builds the tooltip content (display name, consumes, produces, requires-as-labels, rules,
   variables), positions it near the cursor.
3. **`hideN8nHoverPayload()`** — hides the tooltip.
4. Wire `mouseenter`/`mousemove`/`mouseleave` listeners onto each node's `<rect>` in
   `renderN8nDiagram`'s existing node-drawing loop.
5. **CSS** — new `.decompose-n8n-tooltip` etc. classes, tokens only, matching the existing
   `.decompose-drawer` styling conventions already established for this app's other
   floating panels.

## Test

Same Playwright-harness convention as 10c/12a: hand-built fixture tree + `N8nWorkflow`,
hover a node, confirm the tooltip shows the real `consumes`/`produces`/`requires`(resolved
to labels)/`rules`/`variables` for that specific node and updates correctly when hovering a
different node; confirm it hides on `mouseleave`.
