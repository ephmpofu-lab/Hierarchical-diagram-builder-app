## Sub-plans

1. **10k-i.connection-arrowheads-and-flow-animation.md** (Medium) — SVG `<defs>` with two
   `<marker>` elements (accent, warning), `marker-end` on every connection path;
   `<animateMotion>` dot on primary-path connections only (everything except
   `local_branch`), direction matching execution order. Self-contained addition to
   `renderN8nDiagram`; no structural risk to existing rendering.
2. **10k-ii.free-node-dragging.md** (Complex on its own — event handling, live path
   recalculation, zoom-aware coordinate math, and a new client-side position-override store
   are four real, interacting concerns) — left-click-drag repositions a node; connections
   touching it redraw live during the drag, not only on drop. Drag delta divided by current
   zoom scale (the spec's own named prior bug). ~3px movement threshold disambiguates click
   from drag on mouseup. Dragged positions live in a new `state.n8nManualPositions` map
   (step_id -> {x,y}), overlaid on the server-computed layout at render time, cleared by
   Auto-arrange (which already exists, 10i) — never persisted server-side, matching this
   app's own standing "stateless per-request" scope decision already used for n8n node
   config (10b-iii's own precedent).
   **Real coupling with 10k-i, flagged before Build starts (not discovered mid-build):**
   10k-i's flow-dot is an `<animateMotion>` element bound to a specific `path`/`d` string at
   creation time; redrawing a connection's `<path d="...">` during a drag does NOT itself
   move an already-running `<animateMotion>` bound to the old string. Every edge touching
   the dragged node must have its own animate element's `path` attribute (or the element
   itself) updated in the same redraw step, not just the visible line -- verified directly
   against real animated dots on the canvas once 10k-i has shipped, not inferred from the
   connection path alone appearing to redraw correctly.
3. **10k-iii.dot-grid-canvas-background.md** (Simple) — CSS `background-image` radial-dot
   pattern on the n8n diagram wrap, low contrast, present in every canvas state.
4. **10k-iv.three-way-mode-toggle.md** (Medium) — `renderCanvasView` restructured so the
   Layer/Sub-task/Atomic-step tree (`renderTreeDiagram`) becomes a third mode
   (`state.mode === "tree"`) instead of an unconditional render stacked above the output
   section; mode toggle becomes `Python | n8n | Tree`. Directly resolves the layout-
   confusion this session already flagged (two diagrams stacked with no visual separation)
   by removing the stacking, not adding a divider. `ARCHITEQ-APP-FLOW.md:66` corrected to
   match once built, per DP12 (a rules/spec-document change triggers a cross-reference
   check before it's complete).

Sequenced 10k-i -> 10k-iii -> 10k-iv -> 10k-ii: arrowheads/animation and the dot-grid are
low-risk and independent, done first; the mode-toggle restructure changes page structure
before the highest-risk item (dragging) has to coexist with it, rather than the other way
around.
