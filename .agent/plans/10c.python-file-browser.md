# Plan 10c: Python Folder/File/Function Browser

**Complexity: Medium.** Multiple new render functions and state, but frontend-only —
no backend or schema changes, confirmed below. Proceeds through Build/Test/Commit per
`~/.claude/CLAUDE.md`'s Autonomy Default without a further pause.

## Requirement

Part of Plan 10 (`10.ui-shell-rebuild.md`). Reproduces `reference/architeq-ux-mockup.html`'s
Level 1 (folder/file) -> Level 2 (functions in a file) -> Level 3 (one function's code)
browser, plus its side panel (the growing, always-complete file view), for Python mode on
the Canvas screen. Interaction and structure exactly as the mockup demonstrates; colors/
fonts from `ARCHITEQ-DESIGN-BRIEF.md`, not the mockup's own palette (resolved theme
decision).

## Key finding that simplifies this: no backend change needed

`decompose.js` already loads the full `DomainTaskTree` into `state.tree` (`GET
/domains/{domain}/tree`, used elsewhere via `state.tree.nodes[id]` lookups) alongside the
flat `RenderedCodeBlock` list in `state.pythonRender` (`POST /render/python`). Every
`RenderedCodeBlock.step_id` is an Atomic step's real id in `state.tree.nodes`, and that
node's `parent_id` chain (Atomic step -> Sub-task -> Layer) already carries everything
needed to reconstruct the mockup's folder (Layer) / file (Sub-task) grouping. This can be
computed entirely client-side, joining data already fetched -- no new endpoint, no new
`RenderedCodeBlock` fields, no `python_renderer.py` change.

## Build

All in `static/js/decompose.js` unless noted.

1. **`groupPythonRenderByFile(tree, pythonRender)`** -- pure function, no side effects.
   For each `RenderedCodeBlock`, look up `tree.nodes[block.step_id]`, walk `parent_id`
   twice to the Sub-task and Layer nodes, group into
   `{ packageName, folders: [{ label, files: [{ label, blocks: [RenderedCodeBlock...] }] }] }`,
   preserving `pythonRender`'s own topological order within each file (never re-sorted).
   `packageName` derived as `` `architeq_${state.domain}/` `` (slugified). A block whose
   step has no resolvable Sub-task/Layer ancestor (shouldn't happen given R2's C4 nesting,
   but not asserted away) falls into a `(root)` catch-all rather than being silently
   dropped -- same "never drop, always account for" posture as NT3's Code-node fallback.
2. **`state.pyBrowser = { level: 1, folder: null, file: null, func: null }`** -- new state,
   reset whenever `state.domain` changes or mode switches away from Python.
3. **`renderPythonBrowser()`** -- replaces the current flat-`<pre>`-blocks branch in
   `renderOutputSection()` for `state.mode === "python"`. Renders breadcrumbs
   (`packageName [/ file.py [/ func()]]`, each segment clickable per its level) and the
   active level:
   - **Level 1**: folder rows (Layer label) containing file rows (Sub-task label + function
     count), matching the mockup's `py-folder-row`/`py-file-row` structure. Click a file ->
     Level 2.
   - **Level 2**: that file's functions in order, each showing its name and (if the
     underlying `TaskTreeNode.notes` is non-empty) a one-line description from `notes` --
     never a fabricated description when `notes` is empty, unlike the mockup's always-present
     `desc` field (real data doesn't guarantee one). Connector dots between consecutive
     functions label the `produces` field flowing from one to the next (mirrors
     `py-func-connector`/`py-func-portlabel`). Click a function -> Level 3.
   - **Level 3**: that function's code (`RenderedCodeBlock.code`) in a code block with a
     copy button, plus a `requires: ... · produces: ...` meta line from the tree node.
     No progressive line-by-line reveal animation here -- that is Plan 10d's scope
     (progressive build), not this static browsing view.
4. **Side panel** (`renderPythonSidePanel(file)`) -- new, separate from the existing node
   detail drawer (`renderNodeDetailPanel`, unrelated: that one is for clicking tree-diagram
   nodes in n8n/canvas mode). Shows the complete file: every function in that file
   concatenated in order, always the full file regardless of which single function Level 3
   is currently showing (matching the mockup's "clicking function 4 without 1-3 first never
   leaves gaps" behavior). Opens automatically when a function is opened at Level 3; a
   close control collapses it. Ported import-derivation heuristic
   (`importTriggers`-equivalent, scanning the concatenated code for patterns like
   `unicodedata\.`, `requests\.`, `log\.(warning|error|info)`) included even though today's
   `render_python` stub code (`... # TODO: implement`) rarely triggers any of them -- this
   is honest: the mechanism is real and will start producing real import lines the moment
   generated code stops being a TODO stub, not before.
5. **CSS** (`static/css/style.css`) -- new classes (`.decompose-py-crumbs`,
   `.decompose-py-folder-row`, `.decompose-py-file-row`, `.decompose-py-func-row`,
   `.decompose-py-func-chain`, `.decompose-py-side-panel`, etc.), styled from
   `ARCHITEQ-DESIGN-BRIEF.md`'s existing tokens (`var(--bg)`, `var(--surface)`,
   `var(--border)`, `var(--accent)`, `var(--text)`, `var(--text-muted)`) -- no new hex
   values, no JetBrains Mono (the shipped app has no separate mono face; code blocks use
   the existing monospace stack already in `style.css`, matching how the tree diagram's
   drawer code snippets are already styled).

## Test

New tests in a `static/js` context is not this project's convention (no frontend test
runner is set up anywhere in this codebase) -- per this project's established, stated
practice (WP19/WP20/AMENDMENT 5's own honesty about no browser automation), verification
here is:
1. A standalone Playwright harness (same reusable pattern established earlier this
   session: serve a scratchpad dir via `python -m http.server`, link the real
   `style.css`, drive the real `state`/`renderBoard()` directly) exercising
   `groupPythonRenderByFile` against a small hand-built `tree`/`pythonRender` fixture (2
   Layers, 2 Sub-tasks each, 2-3 Atomic steps each) -- confirms folder/file grouping is
   correct and order-preserving.
2. Same harness, click-driven: Level 1 -> click a file -> Level 2 shows the right
   functions in the right order -> click a function -> Level 3 shows its real code ->
   side panel shows the complete file with the clicked function scrolled-to.
3. Manual browser walkthrough against the real, already-frozen `rag` domain once a server
   session is available (stated honestly if not available this pass, matching this
   project's established practice of not claiming an unverified live check).
