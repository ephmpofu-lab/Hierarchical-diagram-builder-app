# Plan 10b: n8n Node Tile (Module 10, Dual Labels + Detail Wiring + Configuration)

**Complexity: Complex.** Confirmed by direct reads before writing this plan: the node tile
(`renderN8nDiagram`, just rebuilt in 10a-iii) currently shows only the display name, no real
n8n type string (CR11 requires both); the existing slide-in detail panel
(`renderNodeDetailPanel`, `static/js/decompose.js:461`) already renders an n8n node's
`type`/`parameters` as read-only JSON when `state.mode === "n8n"`, but nothing on the n8n
canvas currently sets `state.selectedNodeId` to open it (only the Tree Diagram's nodes do);
and `rules/n8n_node_schemas.json` has no enum/options metadata per parameter anywhere — only
a flat `default_parameters` dict per node type, so "chip selection" has no real backend-
supplied option list to draw from beyond each schema's own literal default value and
whatever a declared `Variable.default` supplies. Split into sub-plans below per DP5/DP9.

## Sub-plans

1. **10b-i.dual-labels-and-needs-config.md** — Frontend only (`decompose.js`). Adds a
   second, visually distinct label showing the real n8n type string alongside the existing
   display name (CR11: both shown, never merged, never only one) — using the already-real
   `N8nNode.type` field, no new data. Adds a small visual "needs configuration" indicator
   (a dot/badge) on any node whose matched schema has at least one empty-string default
   parameter with no corresponding non-empty declared `Variable.default` — a real,
   mechanically-checkable predicate over data that already exists, not a new AI judgment.
   Unblocked now. **Built, tested, committed.**
2. **10b-ii.detail-panel-click-wiring.md** — Frontend only (`decompose.js`). Wires a click
   listener onto each n8n canvas node (mirroring the Tree Diagram's existing `onAtomicClick`
   pattern) that sets `state.selectedNodeId` and re-renders — reusing
   `renderNodeDetailPanel`'s already-built n8n snippet display verbatim, not building a new
   panel. Depends on 10b-i only for the visual "needs config" badge being present on the
   node being clicked (no hard dependency otherwise). Unblocked now. **Built, tested,
   committed.**
3. **10b-iii.configuration-mechanism.md** — the genuinely new capability: a per-node
   configuration UI (chip selection -> confirm -> collapse, per-parameter input fields with
   live validation) for a node flagged "needs configuration" by 10b-i. **Built, tested,
   committed** — resolved via 2 user decisions (2026-07-31): chips draw from real,
   doc-verified option lists (`httpRequest.method`/`webhook.httpMethod` added to
   `rules/n8n_node_schemas.json`); confirmed values are client-side/session-scoped only,
   merged into the real download at export time. Honest finding along the way: no
   currently-empty real parameter has a real finite option set, so chips and text inputs
   aren't two treatments of the same field — they're the general per-parameter mechanism,
   and today's actual "needs config" fields all land in the text-input branch (verified via
   a synthetic fixture that chips render/validate/save correctly when a real option list
   does exist). **Module 10b (n8n Node Tile) is now fully complete.**

## Open design questions for 10b-iii (not yet resolved)

1. **What does a "chip" actually offer, given no real options metadata exists?** The only
   honest, non-invented data available per parameter is: the schema's own literal
   `default_parameters` value (e.g. `"method": "GET"`), and whatever the tree's own declared
   `Variable.default` supplies. A few node types have real, well-known finite option sets
   from n8n's own docs (e.g. HTTP Request's `method` is genuinely one of
   GET/POST/PUT/PATCH/DELETE) — but hardcoding those per-field would mean extending
   `rules/n8n_node_schemas.json` with real, doc-verified option lists (the same disciplined,
   hand-curated-and-cited process that file's other entries already follow), not a
   generic/invented chip set. Needs a decision: is that extension worth doing now, or does
   v1 skip chips entirely and use plain input fields only (still satisfying "per-parameter
   user-input fields with live validation," just without the chip-selection shortcut)?
2. **Where does a confirmed value live?** No backend endpoint persists per-node
   configuration today (this app's n8n output has always been stateless per render/
   download). Options: (a) client-side only, held in `state` and merged into
   `N8nNode.parameters` at download time (session-scoped, lost on reload/refresh) — matches
   this codebase's existing "stateless per-request execution for v1" standing scope decision
   (`ARCHITEQ-PRD.md`'s own Additional Scope Decision 4); or (b) a real backend endpoint that
   persists configured values against the domain's frozen tree, surviving reload — a genuine
   new persistence surface, not yet designed.
3. **What counts as "collapse"?** A visual state change (badge clears, tile restyles to
   "configured") is unambiguous and cheap. Whether it also means the tile's on-canvas size
   shrinks/hides its now-satisfied config affordance is a smaller styling call, not blocking.
