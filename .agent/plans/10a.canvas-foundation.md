# Plan 10a: Canvas Foundation (Module 10, Layout + Routing + Pan/Zoom)

**Complexity: Complex.** Confirmed by direct reads before writing this plan:
`backend/render/node_mapper.py::map_tree` currently computes positions as a single flat row
(`position=[index * 280.0, 0.0]`, no stage grouping, no row wrap, no branch handling), and
`static/js/decompose.js::renderN8nDiagram` draws every connection as a plain line with no
classification. Bringing this up to CR3/CR4/CR5/CR7/CR15/CR16/CR18 is 4 genuinely separate
pieces, not one pass — split into sub-plans below per DP5/DP9, this file is the index only.

## Sub-plans

1. **10a-i.stage-zone-layout.md** — Backend only (`node_mapper.py`). Computes each Layer's
   non-overlapping vertical zone first (CR15: zone height derived from its own row count,
   never from wherever nodes happen to land), then rows within a zone wrap at ~9-10 nodes
   (CR4), left-to-right in dependency order within a row (CR3, subordinate to CR15).
   Produces per-node `position` (already an `N8nNode` field) plus new stage-zone metadata.
   Pure data computation — testable with pytest against a hand-built tree, no frontend
   change yet. **Built, tested, committed** — new `N8nStageZone` model (deliberately
   separate from `N8nWorkflow`, which is also the literal downloaded workflow.json, per
   CR2); `compute_stage_zones`/`_atomic_steps_by_layer` in `node_mapper.py`; `map_tree`
   now uses real stage-zone positions instead of the old flat single-row formula.
2. **10a-ii.connection-classification.md** — Backend only (`node_mapper.py` or a small new
   function there). Classifies every connection into one of: adjacent-same-row, local
   branch, row-transition, cross-row, cross-stage, long-distance (CR18) — computed from
   10a-i's positions/zones, stored alongside each connection so the SVG Renderer never has
   to re-derive it (CR18's own predicate: classify first, geometry follows, never a single
   generic formula). Also pytest-testable against the same fixture. **Built, tested,
   committed** — `classify_connections`/`_classify_one` in `node_mapper.py`, with the exact
   category boundaries (row_transition vs cross_row; cross_stage vs long_distance) made
   concrete and documented, since CR18's own text doesn't give numeric thresholds for those.
3. **10a-iii.svg-routing-rewrite.md** — Frontend only (`decompose.js`'s `renderN8nDiagram`).
   Rewrites edge-path generation to consume 10a-ii's classification tags: same-row adjacent
   = straight line; everything else = rounded-orthogonal waypoint path through whitespace
   lanes (CR5, CR6), entering the target's normal left input port always (CR16), never
   through an unrelated node's bounding box. Adds visible input/output ports on every node
   (CR7). **Built, tested, committed** — verified live via Playwright (confirmed installed
   and launchable in this environment, correcting this plan's own earlier "no automation"
   caveat): a 3-zone/5-node/4-classification fixture rendered correctly with zero JS errors,
   screenshot-confirmed. Backend wiring simplified from the original plan: `stage_zones`/
   `connection_classifications` were added directly onto `N8nWorkflow` rather than a second
   endpoint, since `decompose.js::downloadWorkflowJson` already whitelists only
   name/nodes/connections before export (confirmed by direct read) — no leak into the real
   downloaded workflow.json.
4. **10a-iv.pan-zoom.md** — Frontend only (`decompose.js`). Middle-mouse-drag pan,
   cursor-centered scroll-wheel zoom, on the n8n canvas SVG. Self-contained interaction
   layer, independent of 10a-i/ii/iii's layout/routing logic — could in principle build
   before them, but sequenced last here since panning/zooming a still-flat-row canvas has
   nothing meaningful to demonstrate yet.

## Explicitly deferred / out of scope for 10a

CR8 (distinct branch output ports/labels) and CR9/CR14 (item-multiplicity, duplicate-step
detection) — these depend on real branch data existing in a tree (Module 5a/decompose
engine territory), not on canvas rendering itself; 10a's job is rendering whatever
requires[]/produces[] structure already exists correctly, not generating new branch
semantics. CR17 (debug info suppression) is a one-line discipline applied inline wherever
10a-i/ii/iii would otherwise be tempted to render row-count/lane-label text — not a
separate sub-plan. The mockup-vs-Design-Brief palette conflict (10.ui-shell-rebuild.md's
own flagged note) — stays flagged, resolved at 10h (reskin), not here; 10a-iii uses
whatever palette is currently shipped, not the mockup's.

## Critical files

- `backend/render/node_mapper.py` — 10a-i (stage-zone + row layout), 10a-ii (connection
  classification)
- `static/js/decompose.js` — `renderN8nDiagram` and its node/edge-drawing helpers — 10a-iii
  (routing rewrite), 10a-iv (pan/zoom)
- `tests/test_engineering_decomposition.py` — new tests for 10a-i/10a-ii
