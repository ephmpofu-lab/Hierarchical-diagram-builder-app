# Plan 10a-i: Stage-Zone + Row-Wrap Layout (CR3, CR4, CR15)

**Complexity: Medium.** Pure backend data computation (`backend/render/node_mapper.py`), no
frontend change, no schema change to the real n8n-exportable shape. Proceeds through
Build/Test/Commit per the Autonomy Default.

## Requirement

Part of `10a.canvas-foundation.md`. Per `rules/principles/n8n-canvas-rules.md`:
- CR15: each top-level stage's (Layer's) vertical zone is allocated first, non-overlapping
  by construction, before any node is positioned.
- CR4: a row wraps at ~9-10 nodes; no snake/reversed-direction rows.
- CR3 (subordinate to CR15): within a stage's zone, nodes lay out left to right in
  dependency order.

Confirmed by direct read before writing this plan: `node_mapper.py::map_tree` currently
computes every node's position as a single flat row (`[index * 280.0, 0.0]`) with no stage
grouping at all — this sub-plan replaces that formula, not an already-correct one.

## Scope decisions

1. **Stage-zone data is a new, separate artifact (`N8nStageZone`), not folded into
   `N8nNode`/`N8nWorkflow`.** `N8nWorkflow` is also the literal payload downloaded as
   `workflow.json` (R14) — per CR2 ("a stage boundary carries no execution meaning"), zone
   geometry is a rendering-only concern and does not belong inside the real, importable n8n
   artifact. `compute_stage_zones` returns zones separately; wiring them into an API
   response for the frontend to actually draw is 10a-iii's job (when the SVG Renderer first
   needs to consume them), not this sub-plan's.
2. **`map_tree`'s existing signature and `N8nNode.position` field are unchanged** — only the
   *values* `map_tree` puts into `position` change, from the flat formula to
   `compute_stage_zones`'s per-stage/per-row computation. Every existing caller
   (`export_workflow`, the existing Node Mapper tests) keeps working unmodified.
3. **A step whose Layer can't be resolved (shouldn't happen in a well-formed tree) falls
   back to the old flat formula** rather than crashing — defensive, matching this
   codebase's standing "never silently drop, never crash on a malformed edge case" posture,
   not a new invented behavior.
4. **Row cap fixed at 10** (CR4's own "~9-10"), matching `_HORIZONTAL_SPACING`'s existing
   fixed-constant posture — not configurable, revisited only if it proves limiting.

## Build (`backend/render/node_mapper.py`)

1. **New model `N8nStageZone`** (`backend/models.py`): `layer_id: str`, `label: str`,
   `x: float`, `y: float`, `width: float`, `height: float`.
2. **`_atomic_steps_by_layer(tree) -> Dict[str, List[TaskTreeNode]]`** — groups the tree's
   already-globally-topologically-ordered Atomic steps by their owning Layer id (via the
   Atomic step -> Sub-task -> Layer parent chain), preserving the global topological order
   within each layer's list.
3. **`compute_stage_zones(tree) -> Tuple[List[N8nStageZone], Dict[str, List[float]]]`** —
   for each Layer in `tree.root_ids` order: computes row count (`ceil(len(steps) / 10)`),
   zone height from header + row count + padding, stacks zones with a running `cursor_y`
   (CR15 non-overlap by construction, not checked after the fact); assigns each step's
   `(x, y)` by its row/column index within its own zone (CR3/CR4).
4. **`map_tree`** — replaces the flat `[index * _HORIZONTAL_SPACING, 0.0]` position with
   `compute_stage_zones(tree)`'s per-step positions (fallback to the old flat formula only
   if a step's layer can't be resolved).

## Test (`tests/test_engineering_decomposition.py`)

1. `compute_stage_zones` produces two non-overlapping zones for a 2-Layer tree (zone 2's
   `y` >= zone 1's `y + height`).
2. Row wrap: a Layer with 12 Atomic steps produces a taller zone (2 rows) than one with 3
   (1 row), and the 11th step's `y` differs from (is greater than) the 1st step's `y`.
3. Left-to-right dependency order within a row: a step that `requires` an earlier step in
   the same row gets a strictly larger `x`.
4. `map_tree` end to end: a 2-Layer tree's second layer's Atomic steps all have a larger `y`
   than the first layer's, confirming the zone-stacking flows through to the actual mapped
   nodes' `position` field.
