# Plan 11i: Completion Tracking (R34-R36, CD9 — the 100% Rule)

**Complexity: Medium.** A shared rollup rule applied to two structurally different trees
(the Workflow Tree has a real `DomainTaskTree` object to walk; the Component Tree only has
flat lists linked by label strings so far — no unified tree object exists yet). Proceeds
through Build/Test/Commit per the Autonomy Default.

## Requirements

- R34: "Every node in either tree, at any depth, carries a completion status
  (`[ ]`/`[-]`/`[x]`), user-settable only on leaf nodes."
- R35: "A non-leaf node's completion status is always computed from its children ... and is
  never directly writable by a user action (CD9, the 100% Rule)."
- R36: "`PROGRESS.md`'s module-level status is generated from tree node statuses, never
  edited directly and independently of them."

## Scope decisions

1. **A shared, tree-agnostic `_rollup_status(child_statuses)` helper**, since CD9's rule
   (`all [x]` → `[x]`; `all [ ]` → `[ ]`; otherwise `[-]`) is identical regardless of which
   tree it's applied to.
2. **Two rollup functions, not one**, because the two trees have genuinely different
   shapes today: `compute_workflow_tree_rollup(tree)` walks the real `DomainTaskTree.nodes`
   parent/children structure bottom-up (Atomic step leaves are user-set; Sub-task and Layer
   are always derived). `compute_component_tree_rollup(capabilities, components,
   attributes)` uses the same label-string linkage `render_component_tree` (11f) already
   established (`Component.realizes_capability`, `Attribute.component_label`) — there is no
   unified Component Tree object yet to walk generically; a future orchestrator sub-plan
   would need to build one before this could be simplified to one shared walker.
3. **R36 (PROGRESS.md generation) is not wired here.** There is no live orchestrator
   assembling a real Component Tree yet (Stages -3 through 0 are still called
   individually, per 11a-11d), so there's nothing real to generate `PROGRESS.md`'s status
   from. This sub-plan builds the rollup mechanism only; wiring it to actually regenerate
   `PROGRESS.md` is a later sub-plan's job once a real orchestrator and a live domain exist.
4. **Enforcing "never directly writable" is structural, not access-controlled.** There is
   no API endpoint yet for setting node status at all (out of scope, same posture as
   11a-11h). The rollup functions always recompute and overwrite non-leaf status
   unconditionally, which is what actually prevents drift — a future endpoint enforcing
   "writes only accepted on leaf nodes" is a separate, later concern.

## Build (`backend/models.py`, `backend/component/engine.py`)

1. **`status: str = "[ ]"`** added to `TaskTreeNode`, `Capability`, `Component`, and
   `Attribute`.
2. **`_rollup_status(child_statuses: List[str]) -> str`** — the shared CD9 predicate.
3. **`compute_workflow_tree_rollup(tree: DomainTaskTree) -> None`** — mutates
   `tree.nodes[*].status` in place, processing Sub-task nodes before Layer nodes (a Layer's
   rollup depends on its Sub-tasks' already-computed status).
4. **`compute_component_tree_rollup(capabilities, components, attributes) -> None`** —
   mutates `.status` in place on `components` and `capabilities` (`attributes` are the
   leaves, user-set, never touched here).

## Test (`tests/test_engineering_decomposition.py`)

1. `_rollup_status`: all `[x]` → `[x]`; all `[ ]` → `[ ]`; a mix → `[-]`; empty list → `[ ]`.
2. `compute_workflow_tree_rollup` on a hand-built tree (2 Layers, each with Sub-tasks/Atomic
   steps in varying completion states) — confirm Sub-task and Layer statuses roll up
   correctly, including a Layer whose Sub-tasks are themselves rolled-up `[-]` values.
3. `compute_component_tree_rollup` — one capability fully complete (all its components'
   attributes are `[x]`), one partially complete — confirm capability/component statuses
   roll up correctly.
