# Plan 11l: `propose_component_tree` Orchestrator (Module 11's Last Deferred Item)

**Complexity: Medium.** All the individual Stage -3 through 0 functions already exist and
are already tested (11a-11d); this wires them into one real pipeline plus real persistence
and minimal API endpoints, mirroring `backend/decompose/engine.py::propose_tree`'s own
established shape for the Workflow Tree. Proceeds through Build/Test/Commit per the
Autonomy Default.

## Requirement

Named as deferred in every one of 11a-11k's own plan files and in `PROGRESS.md`'s Module 11
line: "a real `propose_component_tree` orchestrator tying Stages -3 through 0 together into
one frozen Component Tree object." Not a new R-number — it's the thing that actually makes
R24-R33 usable end to end, the same way `propose_tree` is what makes R1-R9 usable end to end
for the Workflow Tree (Module 5's own docstring: "implements R1 to R9 end to end").

## Scope decisions

1. **Mirrors `propose_tree`'s exact retry shape**: a bounded loop
   (`MAX_COMPONENT_TREE_RETRIES = 3`, same fixed-constant posture as
   `MAX_DECOMPOSITION_RETRIES`) that runs Stage -3 -> -2 -> -1 -> 0 fresh each attempt,
   validates, and on failure re-runs with the specific violations appended to the reasoning
   context — never a per-stage-only retry (same reasoning `propose_tree`'s own docstring
   already gives: simpler, and the pipeline is one-time-per-domain anyway).
2. **CD3's breadth-first rule is the orchestrator's own job now**, exactly as 11c's plan
   file said it would be: decompose *every* capability into components first (one
   `decompose_capability` call per capability), only *then* enumerate attributes for any
   component — never interleaved.
3. **The Output Documentation Gate (11j) splits across draft time and freeze time**,
   matching CD10's own text ("evaluated at freeze time... not a precondition before Stage
   -3 starts"): `propose_component_tree`'s retry loop checks
   `check_no_shared_attributes`/`check_attribute_leaf`/`check_tree_reconciliation`/
   `check_component_rationale_gate` (data already available mid-authoring); the approve
   endpoint additionally re-checks everything plus `check_ui_documentation_gate` (needs the
   `documentation` field, which only exists once a human supplies it before freezing).
4. **Real persistence, mirroring `taxonomy/repository.py`'s exact convention**: a new
   `backend/component/repository.py` (`component_trees/{domain}.json`), not reusing
   `taxonomy/repository.py` itself — the Component Tree and Workflow Tree are companion but
   structurally distinct artifacts for the same domain (flat linked lists vs. a real
   id-keyed node tree), matching how `backend/component/` is already its own package,
   separate from `backend/decompose/`.
5. **New `ComponentTree` container model** (`domain`, `version`, `requirements`,
   `capabilities`, `components`, `attributes`, `documentation`) — the thing that gets
   persisted; everything inside it already exists as a model, this just bundles them into
   one frozen, versioned artifact the way `DomainTaskTree` bundles `TaskTreeNode`s.
6. **Minimal API only, no new frontend UI** — matches Module 11's own top-level plan,
   explicitly out of scope from the start: "Any UI for triggering Stage -3 through 0 beyond
   a minimal API... is a natural follow-up, not required to satisfy R24-R31." Three
   endpoints, mirroring the Workflow Tree's `draft`/`approve`/`GET tree` shape exactly:
   `POST .../component-tree/draft` (body: real `prd_text` + `reasoning_context`, requires
   the domain's Workflow Tree to already be frozen, per CD6 — 404 if not), `POST
   .../component-tree/approve` (re-validates before saving, 422 with real violations if it
   fails, same posture `api_approve_domain` already has), `GET .../component-tree`.
7. **AI prompts are NOT changed to start asking for `rationale`/`is_ui_tagged`.** A
   freshly-drafted tree will have `requires_rationale=False` on every Component (Stage -1's
   prompt doesn't ask for it) — `check_component_rationale_gate` trivially passes, which is
   an honest reflection of what Stage -1 actually produces today, not a fake pass. Teaching
   Stage -1's prompt to flag genuine judgment calls is a real, separate future enhancement,
   not silently bundled in here.

## Build

1. **`backend/models.py`** — `ComponentTree`; `ComponentTreeDraftRequest`
   (`prd_text: str`, `reasoning_context: str = ""`); `ComponentTreeDraftResult` (`domain`,
   `tree`, `validation`); `ComponentTreeApproveRequest` (`tree: ComponentTree`).
2. **`backend/component/repository.py`** (new) — `load_component_tree`/
   `save_component_tree`, byte-identical convention to `taxonomy/repository.py`.
3. **`backend/component/engine.py`** — `MAX_COMPONENT_TREE_RETRIES`;
   `validate_component_tree(tree, workflow_tree, include_documentation_gate) ->
   ValidationResult` (wraps every existing `check_*` function's plain-string messages into
   `PrincipleViolation(principle_id="CD", message=...)`, reusing every check function
   verbatim, inventing no new validation logic); `propose_component_tree(domain, prd_text,
   reasoning_context, workflow_tree) -> Tuple[ComponentTree, ValidationResult]`.
4. **`backend/api.py`** — the 3 endpoints described in scope decision 6.

## Test (`tests/test_engineering_decomposition.py`)

1. `propose_component_tree` happy path: mocked `_ask_json` routed by each stage's own
   distinctive system-prompt marker (same convention `engine.py`'s own multi-stage mocking
   already established), producing a small tree with reconciling attributes/variables
   against a hand-built matching Workflow Tree fixture — confirms `validation.passed` and a
   real, non-empty `ComponentTree` with the CD3 breadth-first ordering actually followed
   (every capability's components exist before any attribute enumeration is even called —
   asserted via call-order tracking in the mock).
2. `propose_component_tree` retry path: first attempt's mocked response produces a
   reconciliation violation (an attribute with no matching Workflow Tree variable), second
   attempt (same mock, keyed by an attempt counter) produces a clean tree — confirms the
   violation was fed back into context and the final result passes.
3. `validate_component_tree` with `include_documentation_gate=True` on a tree with a
   UI-tagged component and no documentation — confirms the R33 violation surfaces through
   the same function real draft-time checks already use.
4. `POST .../component-tree/draft` — 404 when the domain's Workflow Tree doesn't exist yet;
   200 with a real result when it does (mocked AI).
5. `POST .../component-tree/approve` — re-validates and rejects (422, real violation
   payload) a tampered/invalid tree even if the client claims it's fine; 200 + real
   persistence (confirmed via a follow-up `GET .../component-tree`) for a valid one.
