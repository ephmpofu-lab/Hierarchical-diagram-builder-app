assuming R36 was about a generated end-user domain's own Workflow/Component Tree. It is not.
Section 4's own text: "`PROGRESS.md`'s existing Module-level tracking ... becomes the
top-level rollup view of this same [completion-tracking] mechanism ... A Module in
`PROGRESS.md` is `[x]` only when every node beneath its corresponding requirement's tree(s)
is `[x]`." Read together with this project's own actual Development Loop
(`~/.claude/CLAUDE.md`), the real "tree" whose leaf nodes carry `[x]`/`[-]`/`[ ]` status is
ARCHITEQ's *own* build-tracking structure: `.agent/plans/{module}{sub}.md` files, each
already carrying a `## Status` section with `- [ ] Built` / `Tested` / `Committed`
checkboxes I have been flipping by hand all session. R36's real, concrete ask: stop
hand-writing `` `[x]` ``/`` `[-]` ``/`` `[ ]` `` on each Module's line in `PROGRESS.md` and
instead compute it from those already-real checkboxes.

**Confirmed by direct read this rollup is currently drifted from reality**: `.agent/plans/
12a.docs-folder-and-diagram-engine.md` is fully Built/Tested/Committed, but `PROGRESS.md`'s
Module 12 line still reads "Not started" — exactly the kind of silent drift R36 exists to
prevent (DP8, Documentation Sync Is Part of Definition of Done).

## Scope decisions

1. **Only modules with real plan files are computed; modules without any are left
   untouched.** Modules 1-9 predate the per-file `.agent/plans/` convention (no files exist
   for them) — there is nothing real to compute their status from, so the generator leaves
   their existing `PROGRESS.md` lines exactly as they are rather than guessing or resetting
   them to `[ ]`. Only Modules 10, 11, 12 have real plan files today.
2. **A "leaf" plan is any file with its own `## Status` section carrying the three
   Built/Tested/Committed checkboxes**; an "index" file (e.g. `10.ui-shell-rebuild.md`,
   `10a.canvas-foundation.md`, `11.dual-tree-architecture.md`) has no such section and is
   skipped — its own completion is already fully represented by its leaves, per the 100%
   Rule, so it is never double-counted.
3. **Flattened one-level rollup, matching what `PROGRESS.md` actually tracks.** The real
   plan-file tree is arbitrarily nested (Module -> sub-plan -> sub-sub-plan, e.g. 10 ->
   10a -> 10a-i), but `PROGRESS.md` only has one line per Module — every leaf plan whose
   filename starts with a given module's number prefix rolls up directly into that one
   line, regardless of nesting depth. A dedicated, explicit prefix-to-module-heading table
   (not a guessed regex-to-module-number mapping) avoids ever mis-attributing a file, and
   is the one place a new module's plan-file convention gets registered.
4. **Reuses `backend/component/engine.py::_rollup_status` directly** for both the leaf's own
   Built/Tested/Committed rollup and the module-level rollup over its leaves — the exact
   same CD9 predicate this whole app's own completion tracking already uses, not a second,
   separately-invented implementation of the identical rule.
5. **Surgical single-line replacement, not a full-file regeneration.** The script only
   replaces the `` `[ ]`/`[-]`/`[x]` `` token on the line immediately following each
   `### Module N: ...` heading it has real data for; every other line (descriptions, Open
   Blockers, everything else) passes through untouched, so hand-written prose is never
   silently discarded.

## Build (`scripts/generate_progress.py`)

1. `MODULE_PREFIX_TO_HEADING = {"10": "Module 10:", "11": "Module 11:", "12": "Module 12:"}`
   — matched against each `### ` heading line's own text (substring match), not re-derived
   from PROGRESS.md's own numbering scheme.
2. `parse_leaf_status(path) -> Optional[str]` — reads one `.agent/plans/*.md` file; returns
   `None` if it has no `## Status` section with all three checkboxes, else the rolled-up
   `[ ]`/`[-]`/`[x]` via `_rollup_status`.
3. `compute_module_statuses() -> Dict[str, str]` — globs `.agent/plans/*.md`, groups each
   leaf's status by module prefix (extracted from the filename's leading digits), applies
   `_rollup_status` again across each module's leaves.
4. `apply_to_progress_md(statuses, progress_path)` — line-by-line pass: on any line
   matching `` ^`[ \-x]`` ``` -- ` immediately following a recognized `### Module N:`
   heading, replaces just the leading token with the computed status.
5. `if __name__ == "__main__":` runs the above against the real repo paths and writes
   `PROGRESS.md` in place.

## Test (`tests/test_generate_progress.py`, new file)

1. `parse_leaf_status` on a hand-built temp file: all three `[x]` -> `"[x]"`; all `[ ]` ->
   `"[ ]"`; mixed -> `"[-]"`; a file with no `## Status` section -> `None`.
2. `compute_module_statuses` against the real `.agent/plans/` directory: Module 12 (which
   has exactly one leaf, `12a`, fully `[x]`/`[x]`/`[x]`) computes to `"[x]"` — a real,
   verifiable assertion against this repo's own actual current state, not a fixture.
3. `apply_to_progress_md` on a small hand-built PROGRESS.md fixture: confirms only the
   targeted module lines change, every other line (including prose after the em-dash on the
   same line) is preserved byte-for-byte.
