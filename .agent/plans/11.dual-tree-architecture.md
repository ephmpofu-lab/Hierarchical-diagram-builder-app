# Plan 11: Dual Tree Architecture (Component Tree)

**Complexity: Complex.** Broken into sub-plans below per DP5/DP9; this file is the index only, no implementation happens directly against it.

## Scope

Implements R24-R34 (`ARCHITEQ-PRD.md` Section 4, "Component Tree" and "Completion Tracking"
subsections), grounded in `ARCHITEQ-Dual-Tree-Architecture.md`,
`ARCHITEQ-Recursive-Depth-and-Completion-Tracking.md`, and
`rules/principles/component-decomposition.md` (CD1-CD9). Confirmed in scope (not superseded
by the PRD's original Module 1-10 list) via `RULES-INDEX.md`.

Adds a second, structural tree (Capability -> Component -> Attribute Group -> Attribute)
alongside the existing Workflow Tree (Layer -> Sub-task -> Atomic step -> Variable), derived
from the same domain's PRD rather than from a checklist. Both trees reconcile (R29/CD6)
before either is frozen.

## Sub-plans (built one at a time, each its own Plan -> Build -> Test -> Commit loop)

1. **11a.requirements-engineering-stage.md** — Stage -3: extract a requirements list from a
   PRD, each item traced to a PRD requirement ID. R24.
2. **11b.capability-identification-stage.md** — Stage -2: group requirements into
   capabilities, each with `traced_requirements[]`. R25, CD1.
3. **11c.functional-decomposition-stage.md** — Stage -1: decompose each capability into
   components, breadth-first across a capability's components before any one component's
   attributes are enumerated; each component carries `realizes_capability`. R26, CD2, CD3.
4. **11d.component-attribute-enumeration.md** — Stage 0: enumerate each component's
   attributes to single-name/single-type leaves; freezes the Component Tree. R27, CD4.
   Also where R28 (CD5, no two components share an attribute) is enforced as a Validator
   check.
5. **11e.tree-reconciliation.md** — R29 (CD6): validator category checking every Component
   Tree attribute resolves to exactly one Workflow Tree variable and vice versa, before
   either tree freezes.
6. **11f.python-renderer-component-tree.md** — R30 (CD7, CD8): literal branching diagram
   (ASCII-style connectors) retaining Stage -3/-2/-1 provenance branches; one class/module
   per Component, one field per Attribute.
7. **11g.n8n-hover-payload.md** — R31: hover-reveal on n8n nodes showing `requires`/
   `produces`/`rules`, sourced from existing fields, no new data invented.
8. **11h.recursive-depth-removal.md** — Removes `MAX_ATOMICITY_SPLIT_DEPTH` and
   `_C4_LEVELS`'s implicit 3-level assumption (`backend/validator/principles.py`), and
   `decompose.js`'s equivalent layout depth constant; reframes the amended R21/CD9 rule
   (categories, not a depth ceiling) as the actual stopping condition. Applies to both
   trees.
9. **11i.completion-tracking.md** — R34-R36 (CD9, the 100% Rule): `[ ]`/`[-]`/`[x]` on
   every node in both trees, non-leaf status always a rollup of children, never directly
   writable; `PROGRESS.md`'s module status becomes a generated rollup.
10. **11j.output-documentation-gate.md** — R32-R33 (CD10): a `rationale` field on any
    Component (or Atomic step) whose realization was a genuine, non-deterministic choice,
    checked non-empty at freeze/approve time; an App-Flow-equivalent and Design-Brief-
    equivalent required only when a UI-tagged component exists, else explicitly recorded
    "not applicable." Depends on 11d (Component Tree exists) and 11e (freeze/reconciliation
    step exists) for the Python-track half; depends only on the existing Workflow Tree
    approve step for the n8n-track half (no dependency on 11a-11i).

Sub-plans 1-4 are sequential (each stage's output feeds the next). Sub-plan 5 depends on
1-4 and on the existing Workflow Tree. Sub-plans 6-7 depend on 5. Sub-plan 8 is independent
of 1-7 and can be built any time. Sub-plan 9 depends on all of the above existing (it adds
status fields to nodes both trees already have).

## Explicitly deferred / out of scope for this plan

Any UI for triggering Stage -3 through 0 beyond a minimal API + a state in `decompose.js`
(a polished Component Tree authoring screen is a natural follow-up, not required to satisfy
R24-R31 as testable predicates). Any change to the existing, frozen Workflow Tree pipeline
except where sub-plans 5 and 8 explicitly touch it.

## Verification (whole-plan level; each sub-plan also has its own)

1. Each sub-plan's own tests pass in isolation (mocked AI where applicable).
2. Once sub-plans 1-5 are committed: an end-to-end mocked-AI test builds a small Component
   Tree from a hand-built PRD fixture, reconciles against a hand-built matching Workflow
   Tree, and passes R29's check.
3. Once sub-plan 6 is committed: the rendered Python diagram for that same fixture shows
   the provenance branches and one class per component.
4. Full pytest suite green after each sub-plan's commit, not just at the end.
