# Plan 11k: Roadmap + Checklist Render (R37, CD11)

**Complexity: Medium.** One shared, mode-agnostic render function plus two small adapters
(Workflow Tree, Component Tree) that convert each tree's own shape into that function's
generic input — no new AI calls, no new stored data (CD11's own text: "derived entirely
from existing tree fields at render time"). Proceeds through Build/Test/Commit per the
Autonomy Default.

## Requirement

- R37: "Once a domain's tree (Component Tree or Workflow Tree) is frozen, the Python
  Renderer and n8n Renderer can each produce a Roadmap + Checklist view: the tree's nodes in
  topological build order (R10), each showing its current completion status (R34-R36)."
- CD11's predicate: nodes in topological build order, each showing `[ ]`/`[-]`/`[x]`,
  derived entirely from existing fields — never a separately authored/maintained document.

## Scope decisions

1. **One shared render function, reused by both modes — not duplicated per renderer.**
   CD11's own "Applies to" line names both the Python Renderer and the n8n Renderer as
   consumers of the *same* view, which means the Roadmap + Checklist itself is mode-
   independent (it's a textual sequencing + status view, not a Python-code or n8n-JSON
   artifact) — whichever render mode (`Python` or `n8n`) a user picked at the API layer, the
   same underlying roadmap function produces the view. It lives in
   `backend/render/python_renderer.py` alongside the existing Workflow/Component Tree
   renderers, following 11f's own precedent (that file already houses both trees' render
   logic, not literally "Python-only" content) rather than a new module for one small
   function.
2. **Workflow Tree order reuses R10's existing `_topological_order` (Atomic step level),
   walked inside the tree's own Layer/Sub-task nesting.** Layers/Sub-tasks have no
   `requires`/`produces` dependency graph (that only exists at the Atomic step level per
   P4) — their build order is the tree's own `root_ids`/`children` order (the same order
   `compute_workflow_tree_rollup`, 11i, already walks by). Atomic steps *within* a Sub-task
   are ordered via the existing `_topological_order` function (computed globally across all
   Atomic steps, then filtered per Sub-task, preserving relative order) — genuinely reusing
   R10's computation, not re-deriving a second ordering rule.
3. **Component Tree order reuses render_component_tree's (11f) own breadth-first nesting**
   (Capability → its Components → their Attributes, in construction order) — there is no
   dependency graph on this side either; CD3's breadth-first rule already governs this
   tree's build order, and 11f's renderer already walks it in exactly this sequence.
4. **Output is a flat, indented markdown checklist string** (`- [ ] Label`, `  - [x]
   Label`, ...), reusing the `[ ]`/`[-]`/`[x]` convention already established by
   `PROGRESS.md` itself and by 11i's status fields — not a new status vocabulary.
5. **No new stored fields or models.** Every value the render draws on (`label`, `status`,
   `children`/`root_ids` order, `requires`) already exists on `TaskTreeNode`/`Capability`/
   `Component`/`Attribute` — this sub-plan is pure rendering over that existing data, per
   CD11's own text.

## Build (`backend/render/python_renderer.py`)

1. **`render_roadmap_checklist(items: List[Tuple[str, str, int]]) -> str`** — the shared,
   tree-agnostic renderer. Each item is `(label, status, depth)`; renders one markdown
   checklist line per item, indented `depth * 2` spaces: `f"{'  ' * depth}- {status} {label}"`.
2. **`render_workflow_tree_roadmap(tree: DomainTaskTree) -> str`** — builds the `items` list
   by walking `tree.root_ids` (Layers, depth 0), each Layer's `children` (Sub-tasks, depth
   1), each Sub-task's `children` filtered against a single global `_topological_order` call
   over every Atomic step in the tree (depth 2), then calls `render_roadmap_checklist`.
3. **`render_component_tree_roadmap(capabilities: List[Capability], components:
   List[Component], attributes: List[Attribute]) -> str`** — builds `items` by walking
   `capabilities` (depth 0), each capability's matching `components` via
   `realizes_capability` (depth 1), each component's matching `attributes` via
   `component_label` (depth 2), then calls `render_roadmap_checklist`.

## Test (`tests/test_engineering_decomposition.py`)

1. `render_roadmap_checklist`: a hand-built 3-item list with mixed statuses/depths produces
   the exact expected indented markdown string.
2. `render_workflow_tree_roadmap`: a small 2-Layer tree (reusing the same fixture shape as
   11i's `test_compute_workflow_tree_rollup_bottom_up`) — confirm Layers/Sub-tasks/Atomic
   steps all appear, in the right nesting depth and in dependency order among siblings that
   have a `requires` relationship.
3. `render_component_tree_roadmap`: a small tree (reusing the same fixture shape as 11i's
   `test_compute_component_tree_rollup`) — confirm Capabilities/Components/Attributes all
   appear at the right depth, in construction order.
