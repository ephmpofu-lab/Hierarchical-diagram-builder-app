# Plan 13j: Table Detail Panel + SQL View (Data -> Workflow half)

**Complexity: Medium.** New backend endpoint (reuses 13c's existing `render_sql_ddl`
verbatim) + a new drawer, mirroring the existing Node Detail Panel's exact structure.
Proceeds through Build/Test/Commit per the Autonomy Default.

## Requirement

Part of `13.data-architecture-layer.md`. R50 (entity detail panel: id, name, description,
platform, attributes, PK/FK, constraints, relationships, workflow usage, SQL), completes
R49's Data -> Workflow direction (13i built the Workflow -> Data half).

## Scope decisions

1. **A "View details" affordance inside an expanded entity box, separate from the
   click-to-expand/collapse toggle** (13f) — a small text row, `stopPropagation`'d so it
   doesn't also toggle collapse, sets `state.selectedEntityId` and opens the new drawer.
2. **SQL is fetched from a new, real backend endpoint that reuses `render_sql_ddl`
   verbatim** (`GET .../data-architecture/sql`, `text/plain`) — never regenerated
   client-side (R45/R17: one canonical model, SQL never independently derived).
   Shows the whole domain's generated DDL (not a fragile per-entity regex slice out of
   it) — still fully synchronized with the visual definition, just not narrowed to one
   entity's isolated snippet.
3. **Workflow usage is real anchors, cross-referenced by real node labels from
   `state.tree`** — every anchor whose `data_id` matches this entity, showing the real
   Atomic step label + operation (completes R50's "workflow usage"/"node mappings" fields
   and R49's Data -> Workflow direction).

## Build (`backend/data_architecture/engine.py`, `backend/api.py`, `static/js/decompose.js`)

1. **Backend** — `GET /decompose/domains/{domain}/data-architecture/sql` (`Response`,
   `media_type="text/plain"`, reuses `render_sql_ddl` directly on the loaded, frozen
   architecture's entities).
2. **Frontend** — `state.selectedEntityId`, `state.dataArchitectureSql` (cached, fetched
   once per domain on first entity-detail open); `renderErdDiagram`'s expanded-entity
   branch gains a "View details →" row; `renderEntityDetailPanel()` (mirrors
   `renderNodeDetailPanel`'s drawer structure): id/name/description/database, attributes
   with PK/FK/nullable markers, relationships (from/to this entity), workflow usage (real
   anchors + real node labels), and a `renderDrawerSnippet("SQL", ...)` section.

## Test

1. **Backend** — the SQL endpoint 404s for an unknown/unfrozen domain; returns real,
   synchronized DDL (contains the real entity/column names) with `text/plain` content
   type for a frozen one.
2. **Frontend** — standalone Playwright harness: clicking "View details" on an expanded
   entity opens the drawer showing the real name/attributes/PK-FK markers, the real
   relationship, and the real referencing node's label + operation under workflow usage.
   Zero JS errors.
