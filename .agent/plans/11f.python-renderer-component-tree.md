# Plan 11f: Python Renderer for the Component Tree (CD7/CD8)

**Complexity: Medium.** Pure deterministic rendering (no AI call, same posture as the
existing Workflow Tree Python Renderer) but two distinct outputs (an ASCII diagram string
and Python class scaffolding) from the same input data. Proceeds through Build/Test/Commit
per the Autonomy Default.

## Requirement

R30 (`ARCHITEQ-PRD.md`): "The Python Renderer renders the Component Tree as a literal
branching diagram (ASCII-style connectors), retaining the Requirements Engineering/
Capability Identification/Functional Decomposition branches as visible provenance, not only
the Component/Attribute leaves (CD7). Every Component maps to exactly one Python module or
class; every Attribute maps to exactly one field on that construct (CD8)."

## Where this lives

`backend/render/python_renderer.py` — R30's own text names "The Python Renderer" as one
shared concern across both trees (matching how R11's mode selection is one choice covering
both tracks); this is a new function alongside the existing `render_python` (Workflow Tree),
not a separate module. Its imports extend to the Component Tree's models
(`ExtractedRequirement`, `Capability`, `Component`, `Attribute`).

## Build

1. **`backend/models.py`** — new model:
   ```python
   class RenderedComponentModule(BaseModel):
       component_label: str
       code: str
   ```
2. **`_python_type(type_name)`** — maps an Attribute's free-text `type` (e.g. "integer",
   "list") to a real Python type annotation; unrecognized types default to `str` (never
   invented/guessed further than that).
3. **`_py_field_name(name)` / `_py_class_name(label)`** — slug helpers, same shape as the
   existing `_function_name` helper in this file.
4. **`render_component_tree(domain, requirements, capabilities, components, attributes) ->
   Tuple[str, List[RenderedComponentModule]]`**:
   - The ASCII diagram: three top-level provenance branches (Requirements Engineering,
     Capability Identification, Functional Decomposition), per CD7 — Functional
     Decomposition is where Components (grouped under the Capability that realizes them,
     via `Component.realizes_capability`) and their Attributes actually nest, since that's
     where they're semantically produced; the first two branches are flat lists shown for
     traceability, not re-nested trees of their own.
   - The Python modules: one `RenderedComponentModule` per Component (CD8) — a class named
     from the component's label, one field per Attribute (typed via `_python_type`), a
     docstring naming the component. A component with no attributes yet gets a `pass` body,
     never a fabricated placeholder field.

## Test (`tests/test_engineering_decomposition.py`)

1. A small hand-built fixture (2 requirements, 2 capabilities, 2 components split across
   them, attributes on each) — confirm the ASCII diagram contains all three provenance
   branch headers and every requirement/capability/component/attribute name appears in it.
2. Confirm the Python modules list has exactly one entry per component, each with the right
   `component_label`, a real class definition, and one field per that component's own
   attributes (not another component's).
3. A component with zero attributes — confirm its generated class body is `pass`, not an
   invented field.
4. An attribute with an unrecognized type string — confirm it maps to `str`, not a crash or
   an invented type name.
