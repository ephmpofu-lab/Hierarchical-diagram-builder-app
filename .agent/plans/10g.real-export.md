# Plan 10g: Real Python Export

**Complexity: Simple.** n8n's `workflow.json` export already works (R14,
`n8n_exporter.py`); this sub-plan adds the missing Python-side equivalent: a real,
downloadable zip of the domain's actual module structure. Depends on 10c (the Python
folder/file/function browser, already built, already computes the exact folder/file
grouping this sub-plan needs — server-side, not just client-side). Proceeds through
Build/Test/Commit per the Autonomy Default.

## Requirement

Part of `10.ui-shell-rebuild.md`: "Export produces real files (a downloadable zip/tree of
the Python module structure) or real `workflow.json` (already exists per R14/
`n8n_exporter.py`)."

## Key finding

Traced directly: Python mode has no download control at all today — only n8n mode has a
"Download workflow.json" button (`renderOutputSection`). `decompose.js::
groupPythonRenderByFile` (10c) already computes exactly the folder(Layer)/file(Sub-task)
grouping a real Python package needs, but only client-side, for browsing — there's no
mechanism to turn it into an actual `.zip` a user can download and run. Building a zip
client-side would mean pulling in an external JS zip library (this app has zero external
JS dependencies anywhere else, confirmed by its own SVG-only-via-DOM-API precedent);
Python's stdlib `zipfile` makes a backend endpoint the clean, dependency-free choice,
mirroring `n8n_exporter.py`'s own "renderer computes content, a sibling exporter packages
it into the final downloadable artifact" split.

## Scope decisions

1. **New `backend/render/python_exporter.py`**, mirroring `n8n_exporter.py`'s naming and
   role exactly: `render_python`/`python_renderer.py` computes code, this module packages it
   into `architeq_{domain}/{layer_slug}/{sub_task_slug}.py` files inside a real in-memory
   zip (`io.BytesIO` + `zipfile.ZipFile`), plus an `__init__.py` per folder and one at the
   package root.
2. **Grouping mirrors `groupPythonRenderByFile` exactly, now server-side** — folder =
   Layer, file = Sub-task, same parent-chain walk, same "never silently drop an unresolved
   block" fallback (a `(root)`/`(unresolved)` bucket, matching the frontend's own posture).
3. **Slugging reuses `_function_name`** (`python_renderer.py`) for folder/file names — the
   exact same collapsing algorithm the frontend's `pySlug` already mirrors independently;
   no new slugging logic invented.
4. **One new endpoint**, `POST /decompose/render/python/export`, returning raw zip bytes
   with `Content-Disposition: attachment` — not reusing the existing `render/python` JSON
   endpoint's response shape, since a zip and a `List[RenderedCodeBlock]` are genuinely
   different artifacts for genuinely different purposes (browsing vs. downloading).

## Build

1. **`backend/render/python_exporter.py`** (new) — `_group_blocks_by_folder_and_file`,
   `export_python_package(domain, tree) -> bytes`.
2. **`backend/api.py`** — `POST /decompose/render/python/export`, 404 for an unfrozen
   domain (matching every other render endpoint's existing posture).
3. **`static/js/decompose.js`** — `downloadPythonPackage(domain)` (fetch + blob download,
   mirroring `downloadWorkflowJson`'s existing pattern); a "Download Python package (.zip)"
   button added to `renderOutputSection`'s Python branch, symmetric with n8n's own download
   button placement.

## Test

1. **Backend** — `export_python_package` on the real frozen `rag` tree: the zip's real
   entries include the expected package/folder/file names (derived from `rag`'s own real
   Layer/Sub-task labels) and every entry's content is real, non-empty Python source
   (contains `def `); the endpoint returns `200` with `Content-Type: application/zip` and a
   `Content-Disposition` header, `404` for an unknown domain.
2. **Frontend** — standalone Playwright harness: clicking the download button issues the
   real `fetch` call with the current domain; a stubbed response confirms the download flow
   completes without error. Zero JS errors.
