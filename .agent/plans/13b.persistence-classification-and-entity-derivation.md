# Plan 13b: Persistence Classification (Stage 5) + Entity Derivation (Stage 6)

**Complexity: Medium.** Two AI-calling functions, following the established `_ask_json`
convention (`backend/component/engine.py`'s own precedent). Proceeds through
Build/Test/Commit per the Autonomy Default.

## Requirement

Part of `13.data-architecture-layer.md`. R42 (per-step CRUD/TRANSIENT classification), R43
(deduplicated, stable-Data-ID entities).

## Scope decisions

1. **Stage 5 classifies one Atomic step at a time** (mirrors Stage 0's own per-component
   shape) — `TRANSIENT` is a real, valid answer (returned as `None`, not stored as a
   `DataAnchor` at all, per 13a's own scope decision 2), not a failure to be retried.
2. **Stage 6 derives entities for a WHOLE domain in one call, not incrementally** —
   resolves OQ8 for entity *derivation* specifically (classification, 13b's other half,
   stays per-step): deduplication genuinely requires the model to see every
   persistence-needing step together, the same reasoning `identify_capabilities` (Stage -2)
   already established for grouping a whole requirements list at once. Per-step-only entity
   proposals would have no way to recognize "two different steps mean the same real table."
3. **N:M relationships are not specially derived** — they emerge naturally as two 1:N
   relationships through a join entity (standard relational modeling), matching this
   corpus's own "don't invent a mechanism a simpler existing one already covers" discipline.
   Every `DataRelationship` is derived directly and only from a real `is_foreign_key`
   attribute pointing at a real `references_entity`.
4. **Entities get stable Data IDs (`D01`, `D02`, ...) assigned in first-appearance order**
   from Stage 6's own response — deterministic given the same input, matching how Stage -3
   preserves the PRD's own requirement ids rather than inventing new ones.

## Build (`backend/data_architecture/engine.py`, new file)

1. **`classify_atomic_step_operation(step, reasoning_context) -> Optional[str]`** — one of
   `CREATE`/`READ`/`WRITE`/`UPDATE`/`DELETE`/`QUERY`, or `None` for `TRANSIENT`.
2. **`derive_data_entities(domain, classified_steps, reasoning_context) -> Tuple[
   List[DataEntity], List[DataAnchor], List[DataRelationship]]`** — `classified_steps` is
   `List[Tuple[TaskTreeNode, str]]` (step + its own already-classified operation, from step
   1, filtered to non-`None`). Assigns stable Data IDs, resolves FK references by name,
   builds anchors from the response's own step-to-entity map.

## Test (`tests/test_data_architecture.py`)

1. `classify_atomic_step_operation`: mocked response `"WRITE"` returns `"WRITE"`; mocked
   `"TRANSIENT"` returns `None`; an invalid/garbage operation string also returns `None`
   (never silently accepted).
2. `derive_data_entities`: two steps that the mock explicitly maps to the SAME entity name
   produce exactly one `DataEntity` (not two) with both steps' anchors pointing at its one
   Data ID; a step with a foreign-key attribute referencing another proposed entity
   produces a real `DataRelationship` resolved to the correct Data IDs (never a broken/
   unresolved reference).
3. Stable Data ID assignment: entities appearing in a fixed mock order always get `D01`,
   `D02` in that same order.
