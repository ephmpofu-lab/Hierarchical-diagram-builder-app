# Plan 13e: Data Architecture API

**Complexity: Simple.** Three endpoints, byte-for-byte mirroring the Component Tree's own
`draft`/`approve`/`GET` shape (11l). Proceeds through Build/Test/Commit per the Autonomy
Default.

## Requirement

Part of `13.data-architecture-layer.md`. Minimal API surface for R41-R50, no frontend yet
(13f-13j build that).

## Scope decisions

1. **Both `draft` and `approve` require the domain's Workflow Tree to already be frozen**
   (404 if not) — R41's own "always derived from an already-frozen Workflow Tree," same
   precondition the Component Tree's endpoints already enforce for CD6.
2. **`approve` re-validates before saving**, exact same posture as `api_approve_domain`/
   `api_approve_component_tree` — never trusts the client's claim that a tree is valid.
3. **SQL DDL serving is deferred to 13j** (the table detail panel/SQL view sub-plan, where
   it's actually consumed) — not bundled into this sub-plan's draft/approve/GET scope.

## Build (`backend/models.py`, `backend/api.py`)

1. **`backend/models.py`** — `DataArchitectureDraftRequest` (`reasoning_context: str =
   ""`), `DataArchitectureDraftResult` (`domain`, `architecture`, `validation`),
   `DataArchitectureApproveRequest` (`architecture: DataArchitecture`).
2. **`backend/api.py`** — `POST /decompose/domains/{domain}/data-architecture/draft`,
   `POST .../data-architecture/approve` (re-validates, 422 on failure, 201 on success),
   `GET .../data-architecture`.

## Test (`tests/test_data_architecture.py`)

1. `draft` — 404 without a frozen Workflow Tree; 200 with a real result when one exists
   (mocked AI).
2. `approve` — re-validates and rejects (422) an invalid architecture even if the client
   claims it's fine; 200 + real persistence (confirmed via a follow-up `GET`) for a valid
   one.
