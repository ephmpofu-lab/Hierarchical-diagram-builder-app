# Plan 11c: Functional Decomposition Stage (Stage -1)

**Complexity: Simple.** Same shape as 11a/11b: one new model, one new AI-calling function,
no schema-breaking changes. Proceeds through Build/Test/Commit per the Autonomy Default.

## Requirement

R26 (`ARCHITEQ-PRD.md`): "The system decomposes each capability into the components
required to realize it, breadth-first across all components of a capability before any one
component's attributes are enumerated; every component carries a `realizes_capability`
field and is rejected if unset (Stage -1, Functional Decomposition; CD2, CD3)."

## What this sub-plan does NOT do

Does not build Stage 0 (Component Attribute Enumeration), does not add an API endpoint. Does
not persist anything. Breadth-first ordering (CD3) is satisfied by construction here: this
function is called once per capability (by the future Stage -1 orchestrator in 11d), never
partially, so there is no interleaving with attribute enumeration to get wrong — CD3's real
enforcement point is 11d's orchestration loop (never starting Stage 0 for any component
until every component for the current capability exists), not this function in isolation.

## Build

1. **`backend/models.py`** — new model:
   ```python
   class Component(BaseModel):
       label: str
       realizes_capability: str
       domain: str
   ```
   `realizes_capability` holds the capability's own `label` (capabilities aren't
   persisted/id-keyed yet at this stage — same in-memory-threading posture as 11a/11b).
2. **`backend/component/engine.py`** — new function:
   ```python
   def decompose_capability(
       capability: Capability, reasoning_context: str
   ) -> List[Component]:
   ```
   One AI call. Prompt: given one capability (its label and traced requirement ids, for
   context), propose the components required to realize it. Every returned component must
   have a non-empty label; a component missing one is dropped (CD2's `realizes_capability`
   requirement is satisfied by construction here, not filtered — every `Component` this
   function returns is stamped with `capability.label` directly, never left to the model to
   supply or omit).

## Test (`tests/test_engineering_decomposition.py`)

1. Mocked `_ask_json` returns 3 well-formed component labels for one capability — confirm
   `decompose_capability` returns exactly 3 `Component` objects, each with
   `realizes_capability` equal to the input capability's label and the right `domain`.
2. Mocked `_ask_json` returns one item with an empty label among two well-formed ones —
   confirm the empty-label item is dropped, the other two are returned.
3. Confirm the prompt passed to `_ask_json` includes the capability's own label and traced
   requirement ids (regression guard).
