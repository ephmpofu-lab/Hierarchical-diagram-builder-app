# Plan 10d: Progressive Build Animation

**Complexity: Medium.** Frontend-only (`decompose.js`/`style.css`). Proceeds through
Build/Test/Commit per the Autonomy Default.

## Requirement

Part of `10.ui-shell-rebuild.md`: "the build-status line sequence (Workflow Tree stages
only, per the resolved blocker 4) + streamed reveal of Layer/Sub-task/Atomic-step nodes +
auto-fix-on-failure sequence."

## Key finding that changes the scope honestly

Traced `backend/decompose/engine.py::propose_tree` directly before building this: its
correction loop (propose -> validate -> retry with the specific violation fed back, up to
`MAX_DECOMPOSITION_RETRIES = 3`) runs entirely **inside the single synchronous `/draft`
HTTP call**. `DomainDraftResult` only carries the *final* attempt's `tree`/`validation` --
there is no per-attempt progress, no retry count, nothing that would let the frontend show
a real "watch it find an issue and fix it live" sequence, because that fixing (if any
happened) already finished before the HTTP response ever arrives. The reference mockup's
`runBuildSequence(withFailure)` scripts that moment with fixed `setTimeout` delays and a
demo-only failure flag -- it is choreography, not a reflection of real backend timing.

Building a genuinely live per-attempt animation would require new async infrastructure
(a `Cycle`-style background job + polling, mirroring the existing Reasoning/Decomposition
Cycle pattern elsewhere in this app) -- a real, separate scope expansion, not "animate what
the draft endpoint already does." Consistent with this project's standing refusal to fake
liveness (every other animation-adjacent decision this session has been explicit about real
vs. simulated), this sub-plan does NOT build a fake "auto-fix resolving before your eyes"
sequence. Instead:

- While the `/draft` request is in flight, one honestly-generic "pending" line is shown
  (we genuinely don't know which internal stage is running).
- Once the real response arrives, a sequence of **real, computed-from-the-actual-tree**
  status lines reveals (layer/sub-task/atomic-step counts, grounding simulation, atomicity
  validation) -- paced with small delays purely for readability, not simulating unknown
  backend timing.
- If the final validation still has violations (retries exhausted), the last line honestly
  shows the real issue count in a failed/warn style, then flows into the *already-existing*
  `reviewing_draft` view (violations list + disabled Approve) for human review -- no fake
  self-healing theater.
- A true live per-attempt progress feed is named here as a real, separate future
  enhancement, not silently dropped.

## Scope decisions

1. **New `state.draftRevealLines: []`** — an ordered list of `{text, status}` drives the
   build-status panel in the `drafting` view. Reset at the start of `startDrafting`.
2. **`revealDraftSummary(draft)`** — a small async function, run once the real `/draft`
   response arrives (still within `state.view === "drafting"`), that progressively appends
   real, computed lines to `state.draftRevealLines` with short paced delays, then
   `startDrafting` transitions to `reviewing_draft`.
3. **`reviewing_draft` upgrades from a plain nested-`<ul>` outline to the real
   `renderTreeDiagram`** (`renderTreeOutline`'s own comment already flagged this as a
   temporary simplification) -- this is where "streamed reveal of Layer/Sub-task/Atomic-step
   nodes" concretely happens: Layer nodes fade in, then Sub-task nodes, then Atomic steps
   one at a time, only the first time a given draft is shown (`state.treeRevealed`, reset
   per fresh draft). Node click is a no-op here (the slide-in detail panel isn't wired to
   `reviewing_draft` -- only to the frozen `canvas` tree via `state.tree`); this is not a
   regression, the plain outline was never clickable either.
4. **`canvas` view is untouched** -- by the time a tree is approved and shown there, it's
   already been revealed once during review; no re-animation on every subsequent visit.

## Build (`static/js/decompose.js`, `static/css/style.css`)

1. `state.draftRevealLines: []`, `state.treeRevealed: false`.
2. `startDrafting`: resets both on start; after a successful fetch, calls
   `await revealDraftSummary(draft)` before transitioning to `reviewing_draft`.
3. `revealDraftSummary(draft)`: computes real layer/sub-task/atomic-step counts from
   `draft.tree`, pushes each status line with a short `sleep()` between them; final line
   reflects `draft.validation.passed` honestly.
4. `renderBuildStatusPanel(lines)` + `renderDraftingView()` rewritten to render it.
5. `renderReviewingDraftView()`: replaces `renderTreeOutline` with `renderTreeDiagram`;
   `streamRevealTreeNodes(wrap)` hides then progressively reveals `.level-layer` /
   `.level-sub-task` / `.level-atomic-step` groups, gated by `state.treeRevealed` (set via
   direct mutation, not a `renderBoard()`-triggering state replace, so it doesn't restart
   the animation mid-flight).
6. `style.css`: `.decompose-build-status`/`.decompose-bs-line`/`.decompose-bs-icon` (+ a
   spin keyframe for the pending icon), reusing existing tokens only.

## Test

Standalone Playwright harness: stub `window.fetch` for the `/draft` endpoint to return a
fixed small tree + `validation.passed = true`; call `startDrafting` directly and await it;
confirm `state.draftRevealLines` ends with the correct real counts and a "passed" final
line, `state.view === "reviewing_draft"`, and every tree node's inline `opacity` is `"1"`
after the reveal completes. A second run with `validation.passed = false` confirms the
final line reflects the real violation count in the failed style. Zero JS console errors.
