# Plan 11h: Recursive Depth Reconciliation (R21/CD9 amendment)

**Complexity: Medium.** Turned out smaller than the top-level plan implied, and different
in shape — investigation first, since "remove the depth caps" isn't quite the right fix
once the actual code is traced. Proceeds through Build/Test/Commit per the Autonomy Default.

## What R21/CD9's amendment actually requires

Per `ARCHITEQ-Recursive-Depth-and-Completion-Tracking.md`: "a node that has NOT been split
further purely because a level-count target was reached, while still failing the atomicity
test, is a Validator violation." This does **not** forbid a bounded retry loop (an unbounded
AI-driven split loop is a real infinite-loop risk) — it forbids treating "ran out of
retries" the same as "actually passed."

## Investigation: is `MAX_ATOMICITY_SPLIT_DEPTH` actually a live bug?

Traced `backend/decompose/engine.py`'s split loop
(`_generate_and_test_atomic_steps`): when a candidate still fails after
`MAX_ATOMICITY_SPLIT_DEPTH` retries, it's appended to `accepted` — same as a candidate that
genuinely passed. **But** `backend/validator/principles.py::check_p1_atomicity` (the
whole-tree P1 check that runs as part of `validate_tree`, itself part of `propose_tree`'s
outer `MAX_DECOMPOSITION_RETRIES` correction loop) calls the exact same
`check_atomicity_for_node` function against every atomic step in the *assembled* tree. A
depth-capped-but-still-failing node is genuinely re-checked here and **does** surface as a
real violation, triggering the outer retry with that violation fed back to Stage 3's
prompt. **Conclusion: not a live bug for the Workflow Tree side** — the two-layer system
(bounded inner loop + outer whole-tree re-validation using the identical test function)
already satisfies R21/CD9's real intent. What's missing is a clarifying comment: the
constant's name and the existing code read like a depth ceiling, without stating that
hitting it is caught later, not silently accepted.

## Investigation: the Component Tree side (11d) has a real, missing gap

`backend/component/engine.py::enumerate_attributes` (sub-plan 11d) has the identical
bounded-split-loop shape (`MAX_ATTRIBUTE_SPLIT_DEPTH`) — but **no equivalent whole-tree
re-check exists yet**. Unlike the Workflow Tree, a depth-capped-but-still-compound
attribute name has nothing catching it later. This is a real gap in 11d's own work,
surfaced only now by actually applying R21/CD9's amendment to it. This sub-plan fixes it.

## Build (`backend/decompose/engine.py`, `backend/component/engine.py`)

1. **`backend/decompose/engine.py`** — clarifying comments only, no behavior change:
   at `MAX_ATOMICITY_SPLIT_DEPTH`'s definition and at the split loop's
   `depth >= MAX_ATOMICITY_SPLIT_DEPTH` branch, stating explicitly that this is a
   runaway-loop safety bound, not a depth ceiling — a candidate that hits it is not
   considered atomic; `check_p1_atomicity`'s later whole-tree pass (same
   `check_atomicity_for_node` function) is what actually catches it, per R21/CD9.
2. **`backend/component/engine.py`** — new function:
   ```python
   def check_attribute_leaf(attributes: List[Attribute]) -> List[str]:
   ```
   The Component Tree's missing equivalent of `check_p1_atomicity` — re-checks every
   attribute name in the full list against `_attribute_needs_split` (the same test
   `enumerate_attributes`'s inner loop already uses) and returns one violation message per
   attribute whose name still requires splitting. This is the real safety net 11d was
   missing: a depth-capped-but-still-compound attribute name (from `enumerate_attributes`)
   is no longer silently treated as a leaf.
3. Same clarifying-comment treatment at `MAX_ATTRIBUTE_SPLIT_DEPTH`'s definition, now that
   `check_attribute_leaf` exists to make the "caught later, not silently accepted" claim
   actually true.

## What this sub-plan does NOT do

Does not wire `check_attribute_leaf` into an orchestrator — there isn't one yet for the
Component Tree (Stage -3 through 0 are still called individually, per 11a-11d; a real
`propose_component_tree` orchestrator, analogous to the Workflow Tree's `propose_tree`, is
out of scope for this sub-plan and not yet part of the numbered sub-plan list). Does not
change `_C4_LEVELS` in `backend/validator/principles.py` — traced and confirmed this is a
set of 3 *named categories* (Layer/Sub-task/Atomic step), not a recursion-depth cap; R21/
CD9's amendment is about recursion depth *within* a category, which doesn't touch this
constant at all.

## Test (`tests/test_engineering_decomposition.py`)

1. `check_attribute_leaf` with a fully-split (all-leaf) attribute list — confirm zero
   violations.
2. `check_attribute_leaf` with one attribute whose name still contains "and" — confirm
   exactly one violation naming it.
